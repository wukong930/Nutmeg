# 测量归档 —— 跨 source 去重 vs σ_P 按 source 分组:口径不一致值多少

**日期** 2026-08-13 · **性质** 只读测量,**未改任何生产代码或数据**
**触发** 2026-08-12 盘面快照上线前审计的一条顺带发现
**方法** 10 个 agent(5 测量角度 × 各 1 对抗验证),全部只读打开 `data/v4_observation.db`

---

## §0 一句话

**担忧成立但很小(真实损害 ≈2.0pp,不是我最初算的 25.8pp,高估 12.7×),
⛔ 不值得动共享表。⭐ 但测的过程发现:`sigma_p_fit` 按 source 切轨迹
这个轴从一开始就切错了 —— 改分析侧的效应是改表的 2.7 倍,且零波及面。**

## §1 问题是什么

`odds_snapshots` 是共享线史表。写入走 `record_row_snapshot`,
**去重键不带 source**(`observation/odds_snapshots.py:198-209`):

```python
last = SELECT <state cols> FROM odds_snapshots
       WHERE fixture_id = ?          -- 或 (match_date, league, home, away)
       ORDER BY id DESC LIMIT 1
if last is not None and tuple(last) == state: return False   # 线没变,不写
```

而 `sigma_p_fit` 把轨迹按 **(home, away, date, source)** 分组,并要求
「最靠近开球的点 ≤1.5h」(`_ANCHOR_MAX_H`),否则**整条轨迹丢弃**。

⇒ 谁先抓到一次线变化谁「认领」,另一个 source 那一刻就算也抓了也被吞 ——
它的轨迹被打洞,可能因此掉出闸。**数据地基与分析口径不一致。**

---

## §2 我最初的估计错在哪

我用「并集能过闸 vs 自己能过闸」当损害上界:

| | 轨迹 | 占比 |
|---|---:|---:|
| 现状过闸 | 749 / 2470 | 30.3% |
| 若按并集 | 1386 / 2470 | 56.1% |
| **差** | **637** | **25.8pp** |

**这个上界两个方向都错。**

### 错误一:混淆了「被抢走」和「本来就没在那时抓」

各 source 的作息完全不同,而闸要的是**开球前 1.5 小时内有观测**:

| source | 排程 | 落进 h≤1.5 的比例 |
|---|---|---:|
| `closing` | `StartInterval=1800`,每 30 分,唯一贴开球跑的 | **21.2%** |
| `predict_log` | launchd UTC 01:00 / 07:30 / 13:00,每次跑 ~6 秒 | 2.1% |
| `cup_market` | owner 开面板 + 5 窗/天 cron(08-12 起) | 2.3% |
| `sp_calc` | 同上 | 2.8% |
| `ingest_odds` | UTC 06 单一晨批 | **0.00%** |

拆开 637 条:

| 归因 | 条数 | 占比 |
|---|---:|---:|
| 该 source 在 [ko−1.5h, ko] **根本没跑过** | **581** | **91.2%** |
| 跑了但那批没碰这个 (联赛,日期) | 23 | 3.6% |
| 够格进一步法医的 | 33 | 5.2% |

**结构性证据(完全绕开「当时在不在跑」这种代理):**
- `predict_log` 掉出的 398 条里 **352 条(88.4%)开球前 90 分钟内调度器根本没触发**;
  而它过闸的 61 条里 **60 条(98.4%)落在触发窗内** —— 近乎完美分离
- `ingest_odds`:全期 45 行,最小 h = **4.25h**,它一次都没进过窗口 ⇒ 33/33 结构性不可能

**安慰剂对照(同钟点、别的日子):** 真实 56 vs 基线均值 82,
McNemar 配对 **z = −5.50 / −3.20 / −3.10 / −0.69**。
抢行假说预测真实活跃度应**高于**基线,实测显著**低于**
⇒ **证据方向是反对抢行,不只是「测不出」。**

### 错误二:「并集」本身不是合法的反事实

按-source 去重下,S 只在**它自己抓的时刻**写行;并集包含了 S 根本没抓的时刻。
反方向也有漏:一场**末段一行都没有**的比赛,按-source 去重下 S 仍可能写出新行
(它比的是自己的上一行)—— 真上界是 ≤712 而非 637。两个方向都偏。

### 🚨 错误三(最致命,前两版都漏了):这 637 条**一场新比赛都不带来**

```
现状过闸 749 条轨迹 → 覆盖 533 场
掉出   637 条轨迹 → 坐落在 429 场
其中全新比赛(现状一条过闸轨迹都没有) = 0 场
⇒ 捞回全部 637 条,比赛覆盖面 533 → 533
```

加进来的是**同一场比赛的第 2/3 个高度相关视角**。
**「+25.8pp」从一开始就不是 25.8pp 的信息量。**

## §3 真正的量:拟合会动多少

按比赛日聚类(55 个)、自举 600 次、配对重采样:

| 口径 | 国内层 σ@3h 变化(H/D/A) | 杯赛层 | 仪表判定翻转 |
|---|---|---|---:|
| **C_exact**(source 进去重键) | **+8.3%** [+3.4,+13.6] / +4.5% / +8.6% · 三条 SIG | 全 null | **0 / 12** |
| **B_pool**(按**比赛**分组) | **+23.7%** [+14.4,+34.1] / +16.4% / +20.0% · 全 SIG | 全 null | 2 / 12 |

- 幂指数 `B` 在 C_exact 下 **6/6 腿的差值区间全含 0**
- 真正被 C_exact 救回的只有 **35 条**(带护栏 22 条),不是 636 条 —— **高估 18 倍**
  (因为「线本来就没动」的轨迹加不加 source 都写不出行)

⇒ **改共享表:效应小、判定 0 翻转、代价大。不做。**

## §4 ⭐ 真正的发现:轴切错了

怀疑者角度实测:**1544/1544 组里各 source 看到的价格完全相同**。

线的走势是**市场的属性,不是观测者的属性**。按 source 切轨迹 = 把同一条
市场轨迹拆成几段互相看不见的碎片。机制也自洽:

```
池化后锚的中位 h  0.307 → 0.156(减半)
每轨点数          9 → 32
杯赛层锚几乎没动(0.490→0.458),而杯赛效应正好 null —— 方向与量级自洽
```

⇒ **现状按 source 切会让锚系统性地离收盘更远,从而低估国内层 σ_P 约 19%。**

修法是改 `sigma_p_fit` 的分组键,**改一行、不碰 `odds_snapshots`**。
草案见 `docs/sigma_p_grouping_axis_prereg_draft_2026-08-13.md`。

## §5 顺带挖出的三个结构性事实(之前没人知道)

### ① 去重其实是**两个池**,不对称

`closing` 的 5,095 行 `fixture_id` **全为 NULL**,其余 23,074 行**全非 NULL**。
⇒ `closing` 走元组查找、**看得见所有人**;其余五源走 `fixture_id` 查找、
**完全看不见 closing**。

重放证据:`closing ← 别的源` 前驱 **1,597 次**;`带 fixture_id 的源 ← closing` = **0 次**。

**所以抢夺是「五源互抢 + 单向抢 closing」,不是对称的。**
这也解释了角度 B 找到的 32 对「同 state 双源」为什么 **100% 是 closing→cup_market**。

### ② ~~34% 的比赛带不止一个 `kickoff_utc`~~ → **实为 3.6%,且不是 bug**

> 🚨 **本条初版写错了,已于同日查根因后更正。原文保留在下方,因为错法本身值得记。**
>
> 原文:「**390 / 1133 场(34%)**同一场在不同 source 下记了不同开球时刻(**常见差 1
> 小时**,如 `cup_market` 记 00:30 而 `predict_log`/`closing` 记 01:30)。」
>
> **两处都错:**
> 1. **390 里 349 场(89.5%)差值是 0 分钟** —— `2026-07-04T13:00:00+00:00` vs
>    `2026-07-04T13:00:00Z`,**同一时刻,只是字符串格式不同**。我拿 `!=` 比字符串
>    当成了比时刻。真正时刻不同的是 **41 场 / 1133(3.6%)**。
> 2. **「常见差 1 小时」** —— agent 给了一个 1 小时的例子,我把它写成了「常见」。
>    实测差 60 分钟的只有 **3 场**;真实众数是 **MLS +10 分钟(29 场)**。
>
> ⭐ 又是**「第一条」不是「全部」** + **语法代理测语义属性**(字符串不等 ≠ 时刻不等)。

**根因(2026-08-13 查清)—— 不是数据 bug,是两个上游的两种合法语义:**

| 源 | 字段 | 语义 | 会不会更新 |
|---|---|---|---|
| `closing` | Odds API `commence_time`(`observation/closing_odds.py:169`) | **实际**开球 | ✅ 比赛延后时上游改它 |
| `cup_market`/`predict_log`/`sp_calc`/`ingest_odds` | API-Football `fixture.date` | **排定**开球 | ❌ 从不更新 |

实测证据链:
- **41/41 单调「越记越晚」**,零例外
- 改变时点:27 场在原定开球**前 1 小时内**、6 场在原定开球**之后** —— 延迟开球的签名
- 谁在改:`closing` 29/41、`cup_market` 8/41;`predict_log`/`sp_calc`/`ingest_odds` **0/41**
- 分布:MLS +10min ×29、K1 +30min ×5、+60min ×3(UEL/WC/MLS 各 1)

**✅ 顺手排除了一个真会花钱的假设:** `closing_odds` 靠 `kickoff <= now` 拒收赛中盘
(docstring 记着 2026-07-01 那次赛中捕获造出 +87% 幻影 EV)。开球时刻被上游改晚
⇒ 已开赛的比赛可能重新变成「赛前」。**实测 17 行**确实是在「别的源认为的开球时刻」
之后抓的(全库 17/4035 = 0.42%),但:

```
booksum        1.033–1.059  vs 同批赛前行中位 1.034  ← 同分布
主胜相对移动    中位 1.68% · 最大 15.3%(那场延后整整 1h)
                赛中 1-0 的主胜会移动 30–60%+
⇒ 全部是赛前线。守卫用的是 Odds API 自己的 kickoff,与赔率同源 ⇒ 自洽。
```

**对 σ_P 的影响 ≈ 0:** 逐行 h 与「该场众数开球」的偏差**中位 0.000h**、最大 1.000h;
跨 `_ANCHOR_MAX_H=1.5` 闸**翻转 1 行 / 1464**。

⇒ 这不是待修的缺陷。池化时仍需一条确定性规则(见草案 §3①),但它是**整洁**不是**修复**。

📌 测量中有一版反事实用「首见行的开球时刻」当窗口右端,**静默截掉 5 条真轨迹** ——
已修;那才是真问题(代理选错了端点),和上游语义无关。

### ③ 若真改按-source 去重,队名歧义闸会**反噬**

`_alias_close` / `_club_core_close` 要求 `len({(home,away)}) == 1` 否则 bail(绝不猜)。
实测 `closing` 与 gather 家族共有的 **293 个 club-core 里 24 个(8%)拼法不一致**
(Annecy FC/Annecy、SC Cambuur/Cambuur、Famalicão/Famalicao、
Union Saint-Gilloise/Union St. Gilloise …),现状已有 **23 个 core 键**因此 bail。

按-source 去重 ⇒ closing 对它轮询到的**每一场**都写自己那份拼法 ⇒ 这个数只会涨,
**CLV/软水恰好会在这个兜底函数当初为之而建的那批比赛上丢 join。**
